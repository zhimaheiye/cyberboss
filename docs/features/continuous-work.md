# 持续任务、事件与独立执行会话

## 用户目标与入口

保持现有工作台使用方式，让后台事项能延续进展、接收新的线索，日常聊天及时响应。参考 [DeepSeek Super Agent 原型](https://github.com/deepseek-ai/dsh-superagent-prototype) 中的会话分工、持久工作状态、事件入口和面板反馈思路；沿用本项目的 Codex、OpenTodo、MCP、检索和前端。

- 「交给 Agent」卡片中的「进展与关联」展示摘要、已确认事实及来源、待核验问题、下一步、等待条件、最近执行和提醒决定。
- 同一详情可以补充线索、搜索选择工作台记录、订阅本地文本文件或外部事件。无需新增另一套任务入口。
- 「今天」展示需要处理的事项，点击直接进入详情；普通执行过程仍收起在详情中。
- 设置中的个人工作偏好保留版本。恢复旧文本先载入编辑框，再保存成新版本；默认指令升级不会覆盖个人文本，每次保存也留存当时的默认指令供比较。

## 执行与归属

`agent-pool.js` 管理聊天、后台两个执行通道，最多同时运行一次聊天和一项后台工作。聊天、自然唤醒、每个 job 分别保存 Codex thread ID。首次使用新机制创建干净会话，旧 thread 和历史不删除；聊天注入最近 16 条消息，需要更早信息时通过统一检索读取。

`tool-bridge.js` 在本机请求中携带通道，`run-context.js` 固定每次工具调用对应的运行记录，完成来源、核验、观察、关联不再按“最近运行”猜测归属。两个通道有独立的审批 ID；停止聊天只停止聊天。

`cb_browser` 与需要修改环境的 `cb_maintenance` 按整个运行占用浏览器，其间的命令串行执行。另一通道等待时显示原因；等待超时明确说明动作尚未发送。取消后在途请求结束才释放。该协调只覆盖工作台桥接的浏览器调用，直接使用其它 MCP／浏览器客户端不受此锁约束。提示词要求当前工作流使用桥接工具。

## 进展和事件

`cb_work read/report` 保存当前事项的结构化进展与版本历史。事实带来源，问题与下一步明确记录；仅在实质变化时写进展，正常无变化巡检留运行流水。最近来源尝试和核验缺口会带入下轮。用户补充保留原话与时间，本轮真实的补充确认可通过完成工具代记，仍保留用户来源。

三种显式订阅：

| 类型 | 来源与触发方式 |
| --- | --- |
| reference | 已有统一检索 ref；每分钟比较内容 hash，包含待办完成状态等变化 |
| file | 单个绝对路径的 UTF-8 文本文件，最大 1 MB；每分钟比较正文 hash |
| event | 与 source 名称匹配的外部事件；由已连接的工具或程序主动提交 |

首次订阅建立基线，不启动模型。相同内容不触发；文件在两次采样之间的多次变化合并为最终状态。读取失败记录具体来源和错误，下一轮继续读取，原基线保留。condition 保存“变化后如何跟进”，由 Agent 收到事件后判断；不是模型调用前的语义过滤。

外部入口仍为 `POST /api/events`，本机 Bearer 鉴权。推荐请求形状：

```json
{"source":"device-context","key":"stable-event-id","data":{"summary":"新的设备状态"}}
```

不提供 jobId 时，发给订阅相同 source 的事项；指定 jobId 时定向投递。在保留的事件记录范围内按 `source + key + jobId` 去重。兼容旧的 `{jobId,data}` 请求，服务端生成事件 ID，此兼容形式不能跨请求去重。没有订阅匹配时返回 queued=false。这里提供事件接收能力，未自动安装设备／网站连接器，也没有后台扫描用户所有文件。

事件先落盘，启用且在有效窗口内的事项才执行，静默／暂停／阻塞时保留待处理。每轮接收最多 20 条，新到事件留给后续轮次。事件交给运行后标记已投递并关联结果，不因为进程重启重放有副作用的工作；watch 按已有核验重试规则继续。到点提醒类型的事件直接入提醒箱，不调用模型。

## 可追溯与本机数据

- 每轮保存 Agent 提供的通知理由，以及进程实际的发送、静默、冷却拦截、核验重试或失败结果。
- 技能继续按真实成功证据启用，补充适用前提、重新核验条件；详情显示最近成功时间。
- `desktop.json` 新增 sessionThreads、workStates、workEvents、workSubscriptions、promptPreferences；均属于本机运行数据，不进入公开 Git。
- 进展参与 job 检索，工作事件参与 event 检索；原文仍归到托管事项。开启相应向量来源后，选中的内容会发送到用户配置的向量接口。
- 用户输入、实质进展及其运行证据保留；已投递的普通来源事件跟随符合既有 7 天策略的正常静默运行清理，对应向量同步移除。未处理事件、异常与被引用证据保留。

## 后续：Magpie 低成本模型分工

后续批次已接入 Magpie 配置、模型目录、事项执行器和文本委派，详见[Magpie 接入](magpie.md)。既有事项仍默认使用 Codex，真实任务分配由用户选择。以下保留分工设计依据。

建议把 Magpie 设为唯一外部 API 渠道，先用于提取、整理和检索重排。主 Agent 保留需求理解、授权范围、异常处理及提醒决定。稳定任务的工具执行后续按事项显式选择，并结合已验证技能的适用前提、结果可核验性和历史失败记录提出推荐；初版采用固定分配规则，不为每次分配额外调用模型。

失败升级携带本轮输入、工具结果和未完成步骤，先核对已发生的动作，避免主 Agent 重做已经提交的操作。模型名称不能单独代表价格或可用性，实际路由和计费由 Magpie 管理。当前 API 执行器复用工作台工具，Codex 的其他 MCP 通过交接使用；已设请求次数与输出上限，尚无按金额预算。
